# debate

**Два ИИ-агента спорят о плане, вы решаете. Потом один реализует, другой проверяет.**

> *English summary:* a console orchestrator that makes two coding-agent CLIs (Claude Code, Grok Build, Qwen Code,
> OpenCode) argue about an implementation plan until they agree, escalating to you only on deadlock or critical
> questions, then executes the agreed plan on a separate git branch with a cross-review loop. It drives the official CLIs
> headless, so it runs on your existing subscriptions — no API keys. Linux only (use WSL on Windows).
> Agent prompts are in English; agents write plans and reviews in the language you set (`[rules] language`,
> Russian by default). The console UI is in Russian for now.

Вы даёте задачу или тикет. Автор (по умолчанию Claude Code) пишет план, критик (по умолчанию Grok Build) его разбирает,
они спорят сами, по раундам. Вас зовут, только когда:

- они **договорились** — показывают согласованный план и ждут «го»;
- **не договорились** за N раундов или упёрлись в тупик — показывают обе позиции, решаете вы;
- агенту нужен **ваш ответ** на вопрос, без которого дальше нельзя.

После «го» исполнитель реализует план прямо в репозитории на отдельной ветке, ревьюер проверяет дифф,
исполнитель правит по замечаниям. Коммит и слияние остаются за вами.

Агенты запускаются через свои официальные CLI в неинтерактивном режиме (`claude -p`, `grok -p`, `qwen -p`,
`opencode run`), то есть **на ваших подписках**, без отдельных API-ключей и без оплаты за токены.

Инструкции агентам написаны по-английски: так модели точнее держат формат ответа, и это дешевле по токенам.
Планы, замечания и вопросы агенты пишут на вашем языке — его задаёт `[rules] language`, по умолчанию русский.
Интерфейс консоли — на русском.

## Как устроено

```
задача
  ├─ Критик: независимый разбор, не видя плана (защита от поддакивания)
  ├─ Автор: план v1
  └─ цикл:  Критик → согласен?  ── да ──► plan.md → вы: го / комментарий / выход
              │ нет                                    │ го
              ▼                                        ▼
            Автор: принять / отклонить пункты     ветка → Исполнитель
            план v2 …                                    → Ревьюер → правки …
            тупик или лимит раундов → вы
```

- **Порядок задаёт программа, а не промпт.** Каждый ход агент заканчивает JSON-блоком с вердиктом
  (`agree` / `disagree` / `need_user` …) и списком замечаний с серьёзностью. По этому блоку оркестратор решает,
  кому ходить дальше.
- **Согласие — это отсутствие замечаний уровня blocker и major.** Оставшиеся minor попадают в план отдельным списком;
  исполнитель должен учесть каждое или объяснить отказ, ревьюер это проверяет.
- **Тупик:** автор второй раз подряд отклонил те же существенные пункты — обсуждение сразу передаётся вам,
  не дожидаясь лимита раундов.
- **Сессии постоянные.** У каждой роли своя сессия CLI, поэтому агенту передаётся только новая реплика,
  а не вся история заново.
- **Ваши ответы** уходят обоим участникам как обязательные условия.
- **Состояние сохраняется после каждого шага**: прерванное обсуждение продолжается с теми же сессиями агентов.

## Установка

Работает на Linux. На Windows запускайте через [WSL](https://learn.microsoft.com/windows/wsl/install): CLI агентов
тоже ставятся внутри WSL. Нативный Windows не поддерживается.

Нужны Python 3.11+, git и хотя бы два из поддерживаемых CLI, установленные и авторизованные
(см. [Агенты и модели](#агенты-и-модели)).

```bash
git clone https://github.com/<you>/debate-orch.git
cd debate-orch
pipx install .            # или: uv tool install .   или: pip install --user .
pipx install -e .         # для разработки: правки в коде действуют сразу
```

### Первый запуск: debate init

```bash
debate init               # роли для всех репозиториев → ~/.config/debate/config.toml
debate init --here        # только для этого репозитория → .debate/config.toml
```

`init` ищет установленные CLI (`claude`, `grok`, `qwen`, `opencode`), показывает версии, по вашему согласию
проверяет вход одним коротким запросом к каждому и предлагает раздать роли. Автор и исполнитель — агент, который
лучше пишет код. Критик и ревьюер — по возможности другой: смысл спора в разных моделях. Остальные доступные агенты
становятся запасными. Предложение можно поправить перед записью; остальные разделы конфига не трогаются.

## Проверка агентов: debate probe

Перед первым запуском и после обновления любого CLI:

```bash
debate probe              # агенты, назначенные в [roles]
debate probe qwen opencode
```

Для каждого агента создаётся временный git-репозиторий с README, в котором записан «номер стенда», и делаются
четыре коротких вызова. Результат каждого шага — отдельная строка, зелёная или красная:

| шаг | что делает агент | что проверяется |
|---|---|---|
| 1. ответ разбирается | читает README и отвечает JSON-блоком | CLI запускается и авторизован, вывод разбирается, сессия создаётся |
| 2. сессия продолжается | файл удалён; агента спрашивают номер стенда | ответить можно только из памяти: сессия продолжается и агент работал во временном каталоге, а не там, откуда запущен `debate` |
| 3. разрешение по шаблону работает | выполняет `echo` с выданным разрешением `Bash(echo:*)` | разрешения, которые вы выдаёте по ходу обсуждения, доходят до CLI |
| 4. только для чтения | просят создать файл | в режиме обсуждения файл появиться не должен (`--no-write-check` пропускает шаг) |

Если строка красная:

- **шаг 1** — CLI не установлен, не авторизован (`claude`, `grok auth login`, `opencode auth login`) или поменялся
  формат вывода. Сырой вывод первого вызова показывается в рамке «сырой вывод (1)»;
- **шаг 2** — CLI не возобновляет сессию или работает не в том каталоге. На этапе исполнения второе означало бы
  правки не в той папке (например, мимо worktree), поэтому с таким агентом исполнять нельзя;
- **шаг 3** — CLI не принимает разрешения в том виде, в каком их передаёт адаптер. Флаги можно поправить
  в `[agents.<имя>.options]` без правки кода;
- **шаг 4** — агент может писать файлы во время обсуждения. Не используйте его, пока не разберётесь.

Формулировки шагов намеренно похожи на обычную работу: на просьбы вроде «повтори кодовое слово» модели иногда
отвечают отказом, принимая их за попытку обойти правила.

## Работа

```bash
cd ~/repos/my-project
printf '.debate/*\n!.debate/config.toml\n' >> .gitignore   # обсуждения не в git, конфиг репозитория — по желанию

debate run "Добавить экспорт отчёта в CSV"
debate run -f ticket.md
debate run --no-exec ...      # только обсуждение, без исполнения
debate run --swap ...         # поменять местами автора↔критика и исполнителя↔ревьюера
debate run --worktree ...     # исполнять в отдельной папке-worktree (см. ниже)
debate run --rounds 6 ...     # максимум раундов до эскалации
```

На каждой остановке вы видите план или позиции сторон и выбираете: **го**, комментарий агентам, ответ на вопрос
или выход. Итоговое окно подсказывает команды, чтобы закоммитить, слить ветку и прибраться.

Если ревьюер так и не одобрил изменения за `[exec] max_review_rounds` кругов, debate спросит: ещё круг правок,
комментарий исполнителю, **вернуть план на обсуждение** (когда исполнение показало, что ошибка в самом плане: автор
и критик получат отчёт исполнителя и ревью, пересмотрят план, а исполнитель доведёт уже сделанное до новой версии
в той же ветке), принять как есть или остановиться.

### Где работает исполнитель

**По умолчанию — прямо в репозитории, на новой ветке** `debate/<имя обсуждения>`. Всё на месте: `node_modules`,
`.env`, данные, открытый в IDE проект. После исполнения изменения лежат в этой ветке, проиндексированы, но не закоммичены.

Если в репозитории есть незакоммиченные изменения, перед стартом debate спросит, что с ними делать: спрятать
(`git stash -u`, вернуть потом `git stash pop`), закоммитить самому или исполнять всё равно. Иначе ваши правки
смешались бы с правками агента в диффе для ревьюера. Каталог `.debate/` при этом не учитывается.

**`--worktree`** (или `[exec] use_worktree = true`) — исполнение в отдельной папке `<репо>-wt-<имя>` рядом
с репозиторием. Пока агент работает, вы можете править код и переключать ветки в основной папке. Цена: в worktree
только то, что есть в последнем коммите — нет незакоммиченных правок и файлов вне git (`node_modules`, `.env`, данных),
и после работы папку нужно удалить (`git worktree remove`).

`[exec] branch = false` — исполнять в текущей ветке, без новой.

### Продолжение прерванного обсуждения

```bash
debate list              # незавершённые обсуждения в этом репозитории (--all — все)
debate resume            # продолжить последнее незавершённое
debate resume csv        # или по имени папки / его части
debate resume --role reviewer=opencode   # отдать роль другому агенту (например, у одного кончился лимит)
```

В `state.json` после каждого шага сохраняются этап, раунд, план, ваши ещё не доставленные агентам комментарии
и id сессий. Ход, прерванный на середине, повторяется целиком.

**Ctrl+C** прерывает текущий ход: дальше можно повторить его, дописать комментарий агенту или остановить всё.
В любом меню `q` — остановить или выйти; повторный Ctrl+C или Ctrl+D — тоже остановка с сохранением.
Буквы меню можно вводить и в русской раскладке.

## Конфигурация

Конфиги накладываются слоями, каждый следующий перекрывает предыдущий:

```
встроенные значения
  → ~/.config/debate/config.toml     ваши предпочтения для всех репозиториев
  → <репо>/.debate/config.toml       только то, что отличается в этом проекте
  → --config <файл>                  разовый файл поверх всего
  → --role / --model                 флаги запуска
```

Словари сливаются, списки заменяются целиком. Исключение — `allow_debate` и `allow_exec`: они **дописываются**,
так что право добавляется одной строкой, без копирования стандартного списка:

```toml
# .debate/config.toml в .NET-проекте
[agents.claude]
allow_exec = ["Bash(dotnet build:*)", "Bash(dotnet test:*)"]

[rules]
extra = "Тесты запускать через dotnet test, миграции БД не трогать."
```

Язык, на котором агенты пишут планы, замечания и вопросы, — `[rules] language` (по умолчанию `ru`; можно `en`, `de`…
или название языка). Сами инструкции агентам всегда на английском.

`debate config` показывает итоговые настройки и файл, из которого взято каждое значение (`--all` — все агенты,
а не только назначенные). Пример со всеми ключами — [`debate.example.toml`](debate.example.toml).
Файл `debate.toml` в корне репозитория тоже читается (между общим конфигом и `.debate/config.toml`) — для совместимости.

## Агенты и модели

| kind | CLI | модель (`model`) | что нужно |
|---|---|---|---|
| `claude` | [Claude Code](https://docs.claude.com/en/docs/claude-code) | `opus`, `sonnet` или полный id | вход по подписке (`claude`) |
| `grok` | Grok Build | id из `grok models` | вход по подписке (`grok auth login`) |
| `qwen` | [Qwen Code](https://github.com/QwenLM/qwen-code) | id из `~/.qwen/settings.json` | API-ключ, Coding Plan или локальная модель |
| `opencode` | [OpenCode](https://opencode.ai) | `provider/model` из `opencode models` | ключ провайдера (`opencode auth login`): DeepSeek, Kimi, OpenRouter, локальные Ollama/LM Studio… |

Без `debate init` автор и исполнитель — Claude, критик и ревьюер — Grok. Любую роль можно отдать другому агенту.
Модель необязательна: если не указана, CLI берёт свою модель по умолчанию.

```toml
[roles]
critic = "qwen"            # критиком — Qwen Code
reviewer = "deepseek"      # ревьюером — свой агент, описанный ниже

[agents.qwen]
model = "qwen3-coder-plus"

[agents.deepseek]          # своё имя: несколько агентов одного вида с разными моделями
kind = "opencode"
model = "deepseek/deepseek-chat"
```

### Запасные агенты

Роль можно отдать цепочке агентов:

```toml
[roles]
critic = ["grok", "opencode"]     # основной grok; если у него кончился лимит — opencode
reviewer = ["grok", "opencode"]
```

Если основной агент сообщает, что лимит исчерпан, вход не выполнен или CLI не найден, ход без вопросов переходит
к следующему в цепочке. Новый агент получает вводную: задачу и текущий план, ведь истории прошлого агента у него нет.
Исчерпавший лимит агент до конца обсуждения больше не вызывается и в других ролях. При других ошибках debate
спросит: повторить ход или передать роль запасному. Смена записывается в `transcript.md`.

На один запуск, без правки конфига:

```bash
debate run --role critic=qwen --model qwen=qwen3-coder-plus "..."
debate resume --model claude=sonnet
debate models opencode     # список моделей, если CLI это умеет (grok, opencode)
```

Адаптеры `claude`, `grok` и `opencode` проверены на живых CLI. Адаптер `qwen` написан по документации и покрыт
тестами на имитации — прогоните `debate probe qwen`, прежде чем на него полагаться.

## Права и безопасность

**Обсуждение и ревью — только чтение.** Агентам разрешены инструменты чтения и безопасные команды (`ls`, `cat`,
`rg`, `git log/diff/show`, `pdfinfo`, `jq` …). Команды, которые умеют писать, даже если обычно ими читают
(`find -delete`, `sort -o`), в список не входят. Каждый адаптер держит это своими средствами:

- **claude** — `--allowedTools` со списком и `--disallowedTools` для правок;
- **grok** — `--permission-mode plan` и `--allow` на команды чтения;
- **qwen** — `--approval-mode plan` и `--allowed-tools run_shell_command(<команда>)`;
- **opencode** — конфиг через `OPENCODE_CONFIG_CONTENT`: `bash` по умолчанию `deny`, команды чтения — `allow`,
  правки — `deny`.

**Исполнение** — правки файлов без подтверждения и те же команды чтения. Остальное (сборка, тесты, сеть) — через
`allow_exec` в конфиге или по вашему разрешению по ходу.

**Разрешения по ходу.** Если агент упёрся в запрещённую команду (ssh, curl, запуск скрипта), оркестратор покажет её
и предложит: разрешить по шаблону (`Bash(ssh:*)`), ровно эту команду или свои шаблоны — агент повторит ход
с разрешением; продолжить без неё; больше не спрашивать в этом обсуждении. Для файлов вне рабочего каталога
предлагается доступ только к их папке, для сайтов — только к домену. Разрешения действуют до конца обсуждения,
хранятся раздельно для обсуждения и исполнения: выданное исполнителю не получат критик и ревьюер, и наоборот.

> [!WARNING]
> **Всё, что вы пишете агентам, сохраняется открытым текстом** в `.debate/` (`transcript.md`, `state.json`, `raw/`)
> и уходит провайдерам обоих агентов. Не вставляйте в ответы пароли и токены — дайте агенту путь к файлу или имя
> переменной окружения. И держите `.debate/` вне git.

## Что остаётся после обсуждения

`.debate/<дата>-<задача>/`:

| файл | что внутри |
|---|---|
| `brief.md` | задача |
| `transcript.md` | весь спор по ходам: вердикты, замечания, ответы, ваши решения |
| `plan.vN.md`, `plan.md` | версии плана и итоговый план со статусом |
| `review.json` | ревью диффа |
| `state.json` | состояние для `debate resume` и id сессий (сессию можно открыть и руками: `claude --resume <id>`, `grok -r <id>`) |
| `raw/` | промпт и сырой вывод каждого вызова — для отладки |

В ходах показываются токены из ответа CLI, а не стоимость: всё работает по подписке.

## Ограничения

- Только Linux (на Windows — через WSL).
- Ходы идут последовательно, агенты не работают параллельно.
- Корнем репозитория считается текущий каталог (или `--repo`), а не ближайший каталог с `.git`.
- Интерфейс пока только на русском. Промпты агентам — на английском (модели точнее держат английские инструкции,
  и это дешевле по токенам), а язык, на котором агенты пишут планы и замечания, задаётся `[rules] language`.
- Форматы вывода CLI не везде задокументированы и могут меняться между версиями — для этого и есть `debate probe`.

Что планируется — в [PLAN.md](PLAN.md).

## Разработка

```
src/debate/
  cli.py        команды и консольный интерфейс (rich)
  engine.py     конечный автомат обсуждения: фазы, раунды, эскалация, исполнение, ревью, сохранение состояния
  protocol.py   правила для агентов, промпты, разбор JSON-вердиктов
  agents.py     адаптеры CLI: сборка командной строки, права, разбор вывода, отказы в правах
  config.py     значения по умолчанию и наложение слоёв конфигурации
  gitutil.py    ветка или worktree для исполнителя, stash, дифф для ревьюера
tests/
  test_flow.py  сценарии на имитациях CLI: полный цикл, эскалация, resume, разрешения, адаптеры, конфиги
  fake_agent.py имитация claude / grok / qwen / opencode
```

```bash
python tests/test_flow.py     # или: python -m pytest tests — квоту не тратит
```

Движок не зависит от консоли (интерфейс `engine.UI`), так что поверх него можно сделать веб-интерфейс.
